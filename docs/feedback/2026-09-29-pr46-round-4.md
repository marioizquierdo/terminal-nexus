## Keyboard

### F29 — Can we tell a held key from taps ourselves, instead of the OS key repeat?

> Do we rely on the OS keyboard settings, or can we handle our key-press fate ourselves on the
> terminal? I really hope we can reliably manage key-press vs key-hold on all platforms … when
> tapping, I wish we could move the cursor at regular 1 block intervals. … We can do this on a
> next-iteration.

**Answered, and scheduled.** A classic terminal sends bytes only when a key goes down; while it is
held, the operating system repeats it at its own delay and rate, and nothing says when it is let go —
so today "held" is guessed from the gaps. Newer terminals can report releases: the **kitty keyboard
protocol** (kitty, WezTerm, Ghostty, foot, Alacritty; recent iTerm2 to be measured) marks every key as
press, repeat or release, and Windows Terminal has its own. The browser page always knows. Where
releases arrive, a tap can be exactly one tile and a hold can accelerate until the key is let go,
whatever the OS settings; elsewhere the timing guess stays, tuned by the "Hold window" Experiment.
`node scripts/probe-key-release.mjs` says, in the terminal it runs in, which kind this is. Building
it waits for that measurement in iTerm2 — the next gate after this one.

## Placing buildings

### F30 — Pick a building where the cursor is; the nearest good spot only when it doesn't fit

> Selecting a building should always try the "recommended nearest empty space" for the building, but
> that should be based on the previous cursor location (or on top of the nexus by default), not on the
> last placed building. … They find a nice area and press "b" to build a barracks, the cursor should
> stay at the same position with the barracks selected. The user may place the barracks, then the
> cursor goes back to empty navigation (keeping the menu items visible on the left). The user may decide
> to press "b" again … the cursor moves to the closest available/recommended empty space … (leaving 1
> space with the previous building if possible) … if there's no empty space in 12 tiles around, it
> should stay … move only 1 tile right and 1 tile down, with the ghost building selected (not "x"), and
> if the user tries to place it or decides to move around, then the cursor can change into the default
> "x" … If the users press "esc" it will unselect the building and stay in empty navigation mode …

**Built** in gate 5K. "b" is read as the building's own hotkey (its digit today). Arming a building —
its digit, Enter on its row, or a click on it — keeps the cursor where it is whenever the building
fits there. Where it does not, the cursor moves to the nearest spot within 12 tiles that leaves one
free tile between it and every other building, or, with none in reach, the nearest that fits at all
(nearest by how far the cursor moves, a tile up or down counting as two across, so it moves "only a
few tiles to the right" in most cases; ties go to the more sideways move, then east, then south). With
nothing in reach the cursor steps one right and one down and the building is drawn as itself rather
than as a block of `x`, until you move or try to place. The cursor opens on the Nexus. The old "beside
the last building placed" rule and its "Smart cursor" Experiment are gone. After a placement, or Esc,
the keyboard goes back to where the arming started: a key pressed on the map leaves you on the map,
the menu beside it; anything started on the menu (Enter or a click on a row, or a key pressed while
the menu had the keyboard) goes back to the menu — after a mouse placement "focused but unselected".
Tab now arrives on the map in that same plain navigation; Explore Map is `e`, its row, or Enter on the
map. Pressing a Barracks' key again right after placing one puts the next a free column to its right,
so a run of them builds a row.

### F32 — One "active" style for every menu row

> Menu item selected and active. I think we can standardize on the same style we use for buildings …
> When active, it changes colors and has an extra ">" for emphasis. … "[e] Explore Map", when active,
> it should change into highlighted "> [e] Explore Map" … we can use that same style as the header of
> the exploring details below. Pressing [e] again, or [esc], should be equivalent … Add a line separator
> "---" below the title … Then, the "> [n] Nexus" item should be obvious … I believe after doing this

**Built** in gate 5K. A menu row has two looks: highlighted (the bar, only while the menu has the
keyboard) and active (`>` before it, in the hotkey's colour, its name underlined) while what it does is
under way — a building armed, Explore Map open, the Nexus popup open. One test and one drawing serve
all three, so a later change to the style reaches every row. Explore Map keeps its row at the top of
the panel, active, with a `---` line under it (`───` with Unicode) and the details below; the old
inverse "EXPLORE MAP [esc]" bar is gone. `e` again, Esc, or a click on the panel all go back to where
Explore Map was opened from. The simplification: the Nexus row's special "keep lit behind the popup"
case and the separate Explore Map header both disappeared into the one active style.

## Settings and popups

### F34 — No "now"/"restart" column; a restart warning instead

> Settings don't need to show "now" or "restart". … if a change in settings needs restart, that should
> be a warning on the menu that says "settings need a restart to apply". … This popup does not have an
> action, it's just a warning message. clicking outside or pressing esc should close it.

**Built** in gate 5K. A setting's row is its name and its value, nothing else. A popup can now be a
**message** — a title and text, nothing to choose, closed by Esc or a click outside and by nothing
else — and the first one says "Some settings apply only after a restart: ...". It appears **when
Settings closes** with such a change still pending, rather than at every press of Left/Right: stepping
through a value is not interrupted, putting it back says nothing, and it is said once per change, not
again on the next visit, so he can keep playing and restart later. Starting over moved from Settings to
the game menu as **[r] Restart**; Esc from the message lands on that row. (No Experiment needs a
restart once "Opens on" is deleted (F31), so today the message waits for the next one; the tests
drive it with a list of their own.)

### F36 — A scroll bar in the popup's border

> Settings scrolling with mouse could be implemented on the right border … it only needs to use a
> different symbol to show scroll up and down; clicking on top of the scroll symbol moves the scroll
> up, clicking at the bottom moves it down. … We can safely allow only one scrolling section on the
> whole popup.

**Built** in gate 5K. A popup may have one scrolling list; while it overflows, the right border beside
it is a scroll bar — an up symbol at the top, a down symbol at the bottom, and a track with a solid
thumb showing which part is in view (`^ v :` in plain characters, `▲ ▼ ░` with Unicode). A click on
its upper half scrolls up and on its lower half down; the wheel and the arrow keys work as before.
Settings and the export both have it.

## Found along the way

### F40 — Start the game in a particular state

From F28: a demo, or an agent reproducing a report, should be able to open the Build Phase already
in a state — a power picked, a building placed — rather than asking the player to press the keys.

**Built** in gate 5K: `./bin/terminal-nexus.ts --spike --keys "n 1 1 Enter"` plays those keys
through the real adapters before the player gets the keyboard, and `#keys=` in the browser page's
address does the same; with `--settings` (or `#settings=`) a demo opens exactly where and how it
should. The key names are the scripted playtest's.
