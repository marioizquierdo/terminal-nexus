## Working method

### F18 — The pull request's Demo, sized to the change

> The "Try it" option is excellent. I would change it to "On Claude Web Artifact" (is not just my

nothing) → screenshots → a GIF → a playable page, choosing the cheapest that shows the change.
AGENTS.md and `DEVELOPMENT.md` say the same where they mention the playable page.

## Movement

### F20 — Interpolation, everywhere

> The cursor scrolling on click works really well. Adding the interpolation makes it look a LOT more
> smooth. This is something we can really formalize from all major game engines: interpolations are
> easy and powerful. … Scroll interpolation is awesome and it should probably apply all the time, it
> is a lot easier and better doing large scrolling now.

**Built** in gate 5J: one interpolation module (a "tween": from, to, start, duration, easing curve —
a pure function of time) drives the view's slide and a new cursor glide.

### F21 — Simpler keyboard acceleration; Shift jumps 12

> The slowdown effect after changing direction is not working as expected, but the progressive
> acceleration is working really well … we don't need to implement slow speed. Instead, one keypress
> should move 1, then holding the key (or tapping repeatedly fast) should start scrolling already at
> speed 2, and 300ms later increase speed to 4. Holding shift should behave fundamentally different,
> instead of just speed up to 8, it should move the cursor 12 tiles.

**Built** in gate 5J. The slow-after-a-turn rule is deleted.

## Menu and mouse

### F22 — A click on a menu building arms it at once

> Let's say I am navigating the grid with the mouse, I scroll around a little bit, then I click on the
> "Barracks"; the interface makes it look selected … but instead I keep scrolling. It took me a while
> to realize I needed to click on the menu, and then click again to select the option. I think it
> will be better to focus on the menu AND select the option right away, when doing that, the cursor on
> the grid will already look like the building, then I can keep clicking on the grid with the ghost
> building placement cursor to keep scrolling, and double click will place the building, and get back
> to the menu, focused but unselected. The selected state only makes sense when using the keyboard,
> but using the mouse should activate what is being clicked.

**Built** in gate 5J. This reverses one half of F1 (a first click on the menu only highlighting): a
click now activates what it lands on; the keyboard alone has a "highlighted, not yet chosen" state.

- A click on a building's row arms it at once, whatever had focus: the ghost is at the cursor, the
  map takes the mouse, and the row reads as armed. **Where the ghost appears**: where the cursor
  already is if the map had focus — the spot the player was looking at, always on screen since the
  view follows the cursor — so clicking around the map and then on "Barracks" never carries the view
  back to the base; if the menu had focus, the click is Enter's twin and uses the smart cursor
  beside the last thing planned, as Enter does.
- Clicks on the map then move the ghost; a second click on the same tile places, and the menu comes
  back with **no highlight bar** — nothing looks chosen. The first key pressed on the menu after that
  only shows the bar again (it neither moves nor activates), so a key never acts on a row the player
  could not see.
- **Armed and highlighted now look different.** The inverse bar only ever means "the keyboard is on
  this row, not chosen yet"; an armed row is `>`, bold, in the hotkey colour, with its name
  underlined, and no bar.
- A click on `[n] Nexus` opens its popup at once (disarming, since the click put focus on the menu);
  a click on `[e] Explore Map` opens Explore Map.
- **What made F22 and F23 pull against each other, and how they fit.** Explore Map hides the menu
  behind its panel, so if every click on the map opened it, the Barracks row would be gone the moment
  Mario clicked around the map — the same two-click trap again. So a click on the map *from the menu*
  keeps the menu beside it (the key help says `MAP`; Enter/Space there opens Explore Map), while every
  keyboard way onto the map arrives in Explore Map. Inside Explore Map, a click anywhere on its panel
  gives the menu back and chooses nothing.
- **One thing to feel**: his description has the ghost-carrying clicks "keep scrolling". An armed click
  still never scrolls the view (the confirming click must land on the tile the first one showed);
  Debug Mode's "Armed click scrolls" switches that on if he prefers it.

### F23 — `[e] Explore Map` first, opening the tile panel at once

> The "[e] Explore" option is working very well. Lets do more changes to formalize it. The menu option
> should be on top (first option), renamed to "[e] Explore Map", that should move the cursor and focus
> to the grid, but automatically show the tiles. The popup that shows info about the tiles is great,
> it just needs a header to make it clear this is "Explore Map". Pressing [esc] should get back to the
> menu.

**Built** in gate 5J. `[e] Explore Map` is the menu's first entry and where the keyboard starts;
`e`, Enter on it, a click on it, Tab and a second Right all put the keyboard on the map and swap the
menu for the Explore Map panel, which describes whatever is under the cursor as it moves — no Enter
needed. The panel has a header bar, `EXPLORE MAP` with `[esc]` at its right, and the key help says
`EXPLORE MAP`. Esc (or `x`, or a right click, or a click on the panel) gives the menu back in one step.
The digits still name the building rows only, so no hotkey moved.

## The map's edge

### F25 — A thinner, quieter map border, as Experiments

> The map border looks very good like this as well, although a little thick. I wonder if we could use
> some other border icon, perhaps we can add some options on an experimental flag. I also wonder if it
> would be better to re-use the left border for the menu and place the grid border in there too, let's
> try that for the next iteration, perhaps I can find a symbol that looks better and saves that 1 tile
> column in the UI. The border color should probably be less accentuated. An last, I wonder if the map
> can define different borders to give it personality, it could probably be embedded on the map grid
> design itself, defining custom borders could accentuate the location. For now, let's just add some
> experimental flags to try.

**Built as Experiments** in gate 5J, all three live (they apply the moment they change), all keeping
the rectangle the same weight on every side:

- **Map edge**: the solid bar (as before, the default), a half block on the map's side of the cell, a
  heavy line, a double line, a light shade, or **the map's own**. The thinner ones need the Unicode
  glyph pack (Settings); in ASCII they fall back to the solid bar, and a shade is `:`.
- **Map edge colour**: the frame's own colour (as before), dimmed, or a quieter grey of its own.
- **Shared west side**: the menu's divider doubles as the map's west side and the map gets that
  column (49 tiles across at 80 columns instead of 48). Off by default; with a half block or a line
  the edge no longer reads as a heavy menu border, which is why sharing was undone at F17.
- **A map-defined border**: the map now carries a border style of its own beside its tiles, and "the
  map" shows it. The Build Phase's map (standing in for PERIMETER) names a dashed "fence" — `┅`/`┇` in
  Unicode, `+---+` in ASCII with its posts fixed to the map so they scroll with it. A proof of the
  hook, not map design.
